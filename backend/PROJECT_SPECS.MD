Build the complete backend system for F1 Deals, a car dealership platform, using Node.js, Express.js, PostgreSQL, Prisma, Redis, and Cloudinary. This backend serves two separate frontends: a public client-facing website where visitors browse cars and submit reviews/enquiries, and a private admin panel where a single business owner manages listings, media, and review moderation. Everything described below must be implemented as actual working functionality — do not just scaffold placeholders.

THE FIVE DATA ENTITIES AND WHAT THEY REPRESENT

Admin represents the single business owner who manages the platform. It stores an email address that must be unique, a securely hashed password (never stored in plain text), and timestamps for when the account was created and last updated. There is only ever one admin record, but it must still be a proper database table so the password can be changed through the application itself rather than requiring a code change or redeploy.

Car represents a single vehicle listing. It stores a display title (such as "2019 Range Rover Velar"), the make, the model, the year, the price (always in Ghanaian Cedis, no currency selection needed since the business only ever prices in GHS), the mileage, the transmission type (Automatic or Manual), the fuel type (Petrol, Diesel, Hybrid, or Electric), the body type (a fixed set of categories such as SUV, Sedan, Hatchback, Van, Truck, Coupe — this list should be easy to extend later since the business owner may want to adjust it), the condition (either New or Slightly Used), a free-text description written by the admin, and a status field that is always one of Available, Sold, or Archived. It also stores the exact moment a car was marked Sold, the exact moment it was archived (if applicable), whether the admin has flagged it as a featured car to highlight on the homepage, and standard creation/update timestamps.

CarMedia represents an individual photo or video attached to a car. Each car can have many of these. Each record stores which car it belongs to, whether it is a photo or a video, the actual file URL (hosted on Cloudinary, never stored on the server's own disk), a numeric order value used to control display sequence, and a creation timestamp. The item with the lowest order value is always treated as the cover photo shown on listing cards. Keeping media as its own separate table (rather than a single field on the car) is required so that individual photos/videos can be added, removed, or reordered independently without touching the rest of the car's data.

Review represents a general review of the business as a whole, not tied to any specific car. It stores the reviewer's name, a star rating from 1 to 5, a written message, and a status that is always Pending, Approved, or Rejected. Reviews are publicly submitted by anyone without needing an account, but they never appear publicly until the admin approves them.

Enquiry represents a submission from the financing/trade-in contact form. It stores the sender's name, phone number, an optional email address, their message, a type indicating whether it's a Financing enquiry, a Trade-In enquiry, or a General enquiry, a timestamp recording whether and when an email notification was successfully sent to the admin, and a creation timestamp. This table exists purely to reliably trigger and track the email notification — there is no admin-facing inbox/log screen for it, since email is sufficient for the business owner to see and respond to these.

WHAT THE PUBLIC-FACING API MUST DO

Visitors must be able to retrieve a list of cars with pagination, meaning the response only ever returns a bounded number of results per request along with information on how to fetch the next page — an unbounded list must never be returned. This listing must support filtering by price range, make, year, body type, and condition, applied at the database level so filtering is efficient even as the number of listings grows well past fifty. By default, only cars with status Available or recently Sold should appear (never Archived cars). Visitors must be able to retrieve full details of a single car by its identifier, including its full ordered list of media (photos and the video, if present) and its complete specification data. Visitors must be able to submit a general review consisting of their name, a star rating, and a message — this always gets created with Pending status and never appears publicly until approved. Visitors must be able to retrieve a paginated list of only Approved reviews, along with the overall average rating across all approved reviews, for display on the reviews page and the homepage summary. Visitors must be able to submit an enquiry (financing, trade-in, or general) which is saved to the database and triggers an email to the admin's inbox containing the enquiry details — this email sending must not block or delay the response returned to the visitor, and if the email fails to send, the system must retry rather than silently losing the enquiry.

WHAT THE ADMIN-ONLY API MUST DO

The admin must be able to log in with an email and password, receiving a signed token that proves their identity on subsequent requests — this token must be verified independently on every protected request without relying on any server remembering who is logged in, since multiple server instances may be running simultaneously and any of them must be able to validate any admin's request without needing to share memory with the others. The admin must be able to change their own password at any time through the application. The admin must be able to create a new car listing with all of its specification fields. The admin must be able to update any field of an existing car listing. The admin must be able to explicitly mark a car as Sold, which must record the exact timestamp this happened. The admin must be able to manually delete a car listing entirely at any point, regardless of its status. The admin must be able to retrieve a list of all cars including Sold and Archived ones (unlike the public listing, which hides Archived cars by default), so they have full visibility into their inventory history. The admin must be able to upload multiple photos and a video for a given car, with each upload going directly to Cloudinary rather than passing through or being stored on the application server's own disk — this matters because with multiple server instances running behind a load balancer, any instance might handle any given request, so nothing that needs to persist can live only on one instance's local filesystem. The admin must be able to reorder the media items for a car, which updates their order values so the display sequence (and which item is treated as the cover photo) changes accordingly. The admin must be able to retrieve a list of all Pending reviews awaiting moderation, and approve or reject each one — approving makes it immediately visible on the public reviews page, rejecting permanently hides it.

THE AUTOMATIC SOLD-TO-ARCHIVED BEHAVIOR

When the admin marks a car as Sold, it must remain publicly visible with a clearly marked Sold status for exactly two weeks from that moment, so potential buyers can still see it as social proof that the business is actively selling. After two weeks have elapsed, the car must automatically transition to Archived status without any manual action required, removing it from public visibility while preserving its record in the admin's full inventory view. This automatic transition must be handled by a scheduled background process that runs independently of any individual web request — it must not depend on someone visiting the website to trigger the check, and it must be safe to run repeatedly (for example, running the check twice in a row, or having it happen to run on more than one server instance at the same moment, must never cause errors, duplicate processing, or inconsistent results). At any point before the two-week window elapses, the admin can also choose to delete the car manually instead of waiting for the automatic archive.

CACHING BEHAVIOR

The public car listings query and the public reviews query are read frequently and change relatively rarely, so their results should be cached for a short period rather than hitting the database on every single request. This cache must be stored somewhere shared and accessible to all running server instances (not held in any individual instance's memory), so that no matter which instance answers a given request, it sees the same cached data. Critically, whenever the admin creates, updates, marks sold, or deletes a car, or approves/rejects a review, the relevant cached data must be explicitly invalidated immediately as part of that action — a visitor must never see stale data for longer than it takes the admin action to complete, regardless of the cache's normal expiry time.

RATE LIMITING AND ABUSE PREVENTION

Because reviews and enquiries can be submitted by anyone without an account, both of those submission endpoints must be rate-limited to prevent spam or abuse, and the admin login endpoint must be rate-limited to prevent repeated password-guessing attempts. This rate limiting must be enforced consistently across every running server instance — a visitor should not be able to bypass the limit simply because their next request happened to land on a different instance behind the load balancer.

HORIZONTAL SCALING AND MULTI-INSTANCE REQUIREMENTS

The entire system must be designed to run as multiple identical copies of the same server process simultaneously, sitting behind a load balancer that distributes incoming requests across them, with the ability to add or remove running instances over time as traffic grows or shrinks. This has several concrete consequences that must be respected throughout: no server instance may hold any state in its own memory that matters beyond a single request (no in-memory sessions, no in-memory rate-limit counters, no in-memory caches) — anything that must be shared or remembered across requests belongs in the shared database or the shared Redis store instead. No uploaded file may ever be written to a server instance's local disk, since a different instance may need to serve or reference that file later and would have no way to access another instance's local storage. The scheduled background job for archiving sold cars, and any background job for retrying failed emails, must be coordinated so that having multiple instances running simultaneously never causes the same job to run twice in a conflicting way. The database connection setup must account for many server instances potentially connecting at once, using connection pooling so the total number of open database connections stays within safe limits no matter how many instances are running. Every server instance must expose a simple health-check endpoint that the load balancer can repeatedly call to confirm the instance is alive and its database and Redis connections are working, so that a load balancer can automatically stop sending traffic to any instance that becomes unhealthy. Every server instance must also shut down gracefully when asked to stop — finishing any in-flight requests and cleanly closing its database and Redis connections — rather than abruptly dying, since instances will regularly be started and stopped as part of normal scaling and deployment operations. All configuration (database location, Redis location, Cloudinary credentials, the secret used to sign login tokens, and so on) must come from environment variables so that the exact same server code can run identically across any number of instances without modification.

SECURITY REQUIREMENTS

Passwords must never be stored in a readable form — only as a securely hashed value. Every piece of data submitted by a visitor or the admin (car details, review content, enquiry content, login credentials) must be validated before it is trusted or saved, rejecting anything malformed rather than passing it through to the database. Standard HTTP security headers must be applied to every response. Cross-origin requests must only be permitted from the known frontend website addresses, not left open to any origin. Every error that occurs must be caught and turned into a clean, safe response to the client — raw internal error details or stack traces must never be exposed to whoever made the request. All meaningful server activity should be logged in a structured, consistent format so that logs from many different running instances can be collected and searched together as a single stream, rather than each instance's logs being isolated and hard to correlate.

WHAT EACH FRONTEND CONSUMES FROM THIS BACKEND

The public client website needs: the paginated/filterable car listing, individual car detail retrieval with full media, review submission, approved review retrieval with average rating, and enquiry submission. The admin panel needs: login and password change, full car creation/update/deletion/status-changing, the full (including archived) car listing, media upload and reordering, and review moderation (listing pending reviews, approving, rejecting). Both frontends rely on the same underlying data and business rules described above — there is no duplication of logic between them, only different permission levels applied to the same core system.

Build this as one cohesive, well-organized backend application — not multiple separate services — designed so it can be deployed as several running copies behind a load balancer without any of the problems described above occurring. API CONTRACT — SHARED CONVENTIONS FOR ALL ENDPOINTS

All endpoints are prefixed with /api/v1/ and every response, whether successful or an error, is returned as a JSON object with two top-level fields: a success field that is true or false, and either a data field containing the requested information when successful, or an error field containing a short machine-readable error code and a human-readable message when unsuccessful. Every response uses a standard HTTP status code that matches the outcome — 200 for successful reads, 201 for successful creation, 400 for invalid input, 401 for missing or invalid authentication, 403 for valid authentication without sufficient permission, 404 for a resource that doesn't exist, 429 for rate-limit rejection, and 500 for unexpected server errors. Paginated list endpoints accept a page number and a page size as query parameters, and return, alongside the list of items, the current page number, the page size used, and the total count of matching items, so the frontend can calculate how many pages exist without a separate request.

Authentication works by the admin receiving a signed token upon successful login, which the frontend must then include on every subsequent admin request as a standard Authorization header in the form "Bearer" followed by the token. Any request to an admin-only endpoint missing this header, or containing an invalid or expired token, is rejected with a 401 response before any business logic runs.

PUBLIC ENDPOINTS

Retrieving the car listing accepts optional filters for minimum price, maximum price, make, year, body type, and condition, plus pagination parameters, and returns each car's identifier, title, make, model, year, price, mileage, transmission, fuel type, body type, condition, status, whether it is sold, and its single cover photo URL — full media galleries and description are intentionally left out of the list response to keep it lightweight, and are only included when retrieving a single car's full detail.

Retrieving a single car's detail returns everything included in the list view plus the full description, the complete ordered list of media items each with its type (photo or video) and URL, and the exact date it was marked sold if applicable.

Submitting a review accepts a name, a star rating, and a message, and returns the created review's identifier and a confirmation that it has been submitted for approval — it never returns the review as publicly visible immediately.

Retrieving approved reviews accepts pagination parameters and returns each review's name, star rating, message, and submission date, plus a separately calculated overall average rating and total approved review count for the whole business.

Submitting an enquiry accepts a name, phone number, optional email, message, and a type of financing, trade-in, or general, and returns a confirmation that the enquiry was received — the frontend does not need to know or handle whether the email notification succeeded, since that is retried automatically on the backend.

ADMIN ENDPOINTS

Logging in accepts an email and password and returns a signed token along with its expiry information. Changing password accepts the current password and a new password, requires a valid admin token, and returns a simple confirmation.

Creating a car accepts every specification field described in the schema (title, make, model, year, price, mileage, transmission, fuel type, body type, condition, description) and returns the newly created car's identifier and full details. Updating a car accepts any subset of those same fields for an existing car identifier and returns the updated full details. Changing a car's status accepts the target status of available, sold, or archived for an existing car identifier, automatically records the sold timestamp when transitioning to sold, and returns the updated car. Deleting a car accepts an existing car identifier and returns a simple confirmation, permanently removing the car and its associated media.

Retrieving the full admin car list works like the public listing but accepts an additional filter for status that includes archived cars, and accepts the same pagination and filtering parameters as the public version.

Uploading media accepts one or more files for an existing car identifier along with whether each is a photo or video, uploads them to Cloudinary, creates the corresponding media records, and returns the newly created media items with their assigned order values. Reordering media accepts an existing car identifier and a new ordered list of media identifiers, and returns the updated ordered media list.

Retrieving pending reviews accepts pagination parameters and returns reviews awaiting moderation with the same fields as the public review view. Approving or rejecting a review accepts an existing review identifier and the target status of approved or rejected, and returns the updated review.

This contract must be treated as fixed and consistent — every endpoint built anywhere in this system must follow these same response, pagination, authentication, and error conventions without exception, so that any frontend built against this backend can rely on identical behavior across every single endpoint.
